# 通用数据关系架构优化清单

> 项目：电商数据分析看板  
> 目标：降低系统对 `behavior`、`orders`、`products`、`users` 等固定文件角色的强依赖，让用户上传结构不同的 CSV 后，系统可以通过字段语义和表关系完成数据分析。  
> 实施原则：渐进改造、兼容现有能力、自动发现但由用户确认、低置信度不参与正式计算。

## 1. 当前问题

当前系统主要采用“文件角色驱动”模式：

```text
上传 CSV
→ 判断文件属于哪个固定角色
→ 按角色查找指定字段
→ 使用预先写死的表关系和指标逻辑
```

现有固定角色包括：

```ts
type FileRole =
  | 'behavior'
  | 'orders'
  | 'order_items'
  | 'products'
  | 'users'
  | 'refunds'
  | 'unknown'
```

这种模式存在以下限制：

- 新增一种表结构时，往往需要新增文件角色和专用判断。
- 字段存在但不在预期角色中时，指标可能仍被判定为不可用。
- 两张表拥有明确公共键时，系统也无法自动建立关系。
- 类目、地区、设备、会员等级等对照表无法通用接入。
- 字段映射、指标能力、看板和 AI 上下文之间容易出现状态不同步。
- 固定角色和分支持续增加后，维护与测试成本快速上升。

典型问题：

```text
UserBehavior1.csv
- user_id
- item_id
- category_id
- behavior_type
- timestamp

CategoryTable.csv
- category_id
- category_name
```

两张表可以通过 `category_id` 建立多对一关系，但当前系统没有通用关系模型，因此无法自动用 `category_name` 展示类目排行。

## 2. 目标架构

目标流程：

```text
上传任意 CSV
→ 解析表结构和数据质量
→ 识别字段语义
→ 自动发现候选关系
→ 用户确认或调整关系
→ 构建统一分析模型
→ 根据可解析字段开放指标
→ 看板和 AI 使用同一份实时模型
```

核心改变：

- 文件角色从“功能准入条件”降级为“辅助识别标签”。
- 指标能力从“角色驱动”改成“字段与关系驱动”。
- 表关系从代码中的固定分支改成会话内可配置的关系对象。
- 原始 ID 始终保留，存在可靠对照表时再替换为可读名称。
- 不确定的自动判断只作为建议，不直接影响正式分析。

## 3. 实施边界

### 3.1 第一阶段支持

优先支持安全、常见的维度映射：

```text
业务明细表中的重复 ID
→ 对照表中的唯一 ID
→ 对照表中的名称或属性
```

包括但不限于：

- `category_id → category_name`
- `product_id → product_name`
- `region_id → region_name`
- `device_id → device_name`
- `channel_id → channel_name`
- `member_id → member_level`

第一阶段关系限制：

- 支持一对一和多对一查询关系。
- 维度表连接键必须唯一或近似唯一。
- 允许部分值无法匹配，未匹配值回退显示原始 ID。
- 每个来源字段默认只启用一个主要展示关系。
- 只使用已确认关系参与正式指标计算。

### 3.2 第一阶段暂不支持

- 自动启用多对多关系。
- 复合主键关系。
- 基于名称相似度的模糊连接。
- 无限制的多层跨表关联。
- 任意 SQL、公式或用户脚本。
- 将所有表直接拼接成一张大宽表。
- 在浏览器中无上限处理超大规模数据。

这些能力在确有业务需求后再单独评估，避免引入数据重复计算和性能问题。

## 4. 数据模型改造

### 4.1 通用数据表元数据

- [ ] 为每个上传文件生成稳定的 `tableId`，不要使用文件名作为唯一标识。
- [ ] 保存表名、原文件名、行数、字段数和导入时间。
- [ ] 增加非强制表分类：`fact`、`dimension`、`mixed`、`unknown`。
- [ ] 保留原有 `FileRole`，但仅作为兼容标签和识别提示。
- [ ] 保存字段统计：空值率、唯一值率、样例值、推断数据类型。
- [ ] 为表数据增加版本号，映射或关系变化时递增。

建议结构：

```ts
interface DataTable {
  id: string
  name: string
  sourceFileName: string
  classification: 'fact' | 'dimension' | 'mixed' | 'unknown'
  suggestedLegacyRole?: FileRole
  columns: DataColumn[]
  rows: Record<string, unknown>[]
  dataVersion: number
}
```

### 4.2 通用字段元数据

- [ ] 区分原始字段名、标准语义和业务含义。
- [ ] 保存字段的数据类型与分析角色。
- [ ] 保存自动识别结果、用户确认结果和置信度。
- [ ] 手动映射后立即更新字段语义，不等待重新导入。
- [ ] 保留原始值，标准化只用于比较和计算。

建议结构：

```ts
interface DataColumn {
  sourceName: string
  semanticType?: string
  businessMeaning?: string
  dataType: 'string' | 'number' | 'datetime' | 'boolean' | 'unknown'
  analysisRole: 'identifier' | 'dimension' | 'measure' | 'time' | 'attribute'
  confidence?: number
  confirmedByUser: boolean
}
```

### 4.3 通用关系模型

- [ ] 在 `ImportSession` 中保存候选关系和已确认关系。
- [ ] 关系必须记录左右表、左右字段、基数、匹配率和状态。
- [ ] 增加可选 `displayField`，用于将 ID 映射成名称。
- [ ] 区分自动发现和用户手动创建的关系。
- [ ] 支持确认、修改、拒绝、停用和删除关系。
- [ ] 关系修改后触发分析模型和指标缓存失效。

建议结构：

```ts
interface TableRelationship {
  id: string
  leftTableId: string
  leftField: string
  rightTableId: string
  rightField: string
  cardinality: 'one-to-one' | 'many-to-one'
  displayField?: string
  matchRate: number
  rightKeyUniqueness: number
  confidence: number
  source: 'auto' | 'manual'
  status: 'suggested' | 'confirmed' | 'rejected' | 'disabled'
}
```

## 5. 字段语义识别

- [ ] 统一字段名标准化：大小写、空格、短横线、下划线和常见前后缀。
- [ ] 扩展中英文别名词典，例如 `cate_id`、`categoryId`、`商品类目ID`。
- [ ] 将用户手动配置视为最高优先级，不被后续自动识别覆盖。
- [ ] 对金额字段区分 `paid_amount`、`unit_price`、`line_amount` 和 `refund_amount`。
- [ ] 对时间字段区分行为时间、下单时间、支付时间和退款时间。
- [ ] 对 ID 字段统一采用字符串进行关系比较，保留前导零处理策略。
- [ ] 对混合类型、空值过多和异常格式给出数据诊断提示。

验收标准：

- [ ] `category_id` 不论位于哪种文件角色中，都能被识别为类目标识。
- [ ] 用户手动把字段映射为 `category_id` 后，候选关系和指标能力立即重新计算。
- [ ] 字段语义不再依赖文件名或固定角色才能生效。

## 6. 自动关系发现引擎

### 6.1 候选生成

- [ ] 在不同表之间比较标准语义相同的字段。
- [ ] 优先考虑以 `_id`、`_code`、`编号`、`编码` 结尾的字段。
- [ ] 检查左右字段数据类型是否兼容。
- [ ] 使用样本值交集快速筛选候选关系。
- [ ] 仅对候选关系执行完整匹配率验证，避免所有字段全量两两比较。
- [ ] 同一张表内默认不生成自关联建议。

### 6.2 关系评分

关系置信度至少应综合：

- [ ] 标准语义相似度。
- [ ] 原始字段名相似度。
- [ ] 数据类型兼容度。
- [ ] 实际值重合率。
- [ ] 右侧连接键唯一性。
- [ ] 右侧是否存在名称或属性字段。
- [ ] 两张表的数据粒度特征。

建议阈值：

```text
高置信度：>= 0.85，默认勾选但仍可撤销
中置信度：0.60-0.85，要求用户确认
低置信度：< 0.60，只在高级建议中展示
```

阈值需要通过真实样本和测试调整，不能仅凭字段名直接确认关系。

### 6.3 安全验证

- [ ] 右表连接键重复且对应多个名称时，禁止用于名称映射。
- [ ] 匹配率低于最低阈值时，不自动启用。
- [ ] 同一来源字段存在多个候选维度表时，要求用户选择主要关系。
- [ ] 检测连接后可能造成的数据膨胀风险。
- [ ] 未匹配值显示原始 ID，并在诊断中报告未匹配数量。
- [ ] 保存关系诊断样例，便于用户验证关联是否正确。

## 7. 字段确认页和关系配置 UI

### 7.1 页面布局

- [ ] 保留字段映射区域。
- [ ] 增加“数据关系”区域，展示自动发现的候选关系。
- [ ] 将专业术语转换为普通用户可理解的说明。
- [ ] 默认只展示高、中置信度建议，高级配置折叠。
- [ ] 把不可用指标和数据质量问题统一放入可折叠“数据诊断”。

推荐卡片文案：

```text
发现可用的数据关系

用户行为表.category_id
可以匹配
类目名称表.category_id

匹配成功：98.6%
建议显示：category_name

[确认使用] [修改] [忽略]
```

### 7.2 手动关系配置

- [ ] 支持选择来源表和来源字段。
- [ ] 支持选择对照表和连接字段。
- [ ] 支持选择用于展示的名称或属性字段。
- [ ] 配置过程中实时显示匹配率和唯一性。
- [ ] 不安全关系必须说明原因，不允许静默启用。
- [ ] 保存关系后立即刷新能力清单。

### 7.3 状态同步

- [ ] 字段映射变化后重新发现受影响的关系。
- [ ] 关系变化后重新生成分析模型。
- [ ] 分析模型变化后清除相关指标缓存。
- [ ] 看板、业务建议和 AI 上下文使用同一数据版本。
- [ ] 页面显示“已根据最新配置更新”或明确错误状态。

## 8. 分析模型改造

- [ ] `AnalysisModel` 保留全部通用表，而不是只保留固定角色表。
- [ ] 在模型中暴露已确认关系图。
- [ ] 提供按标准语义查找字段的统一方法。
- [ ] 提供 `resolveDisplayValue`，把原始 ID 映射为名称。
- [ ] 提供按关系筛选和补充维度的安全查询方法。
- [ ] 不把所有表预先拼接成一张大宽表。
- [ ] 每个指标声明自身的数据粒度和主要数据源。
- [ ] 关系不可用时允许指标回退到原始 ID，而不是整体禁用。

建议核心接口：

```ts
resolveField(semanticType: string): ResolvedField[]

resolveDisplayValue(
  tableId: string,
  field: string,
  rawValue: unknown
): string

getConfirmedRelationships(tableId?: string): TableRelationship[]
```

## 9. 指标能力改造

旧逻辑示例：

```ts
if (hasRole('products')) {
  enableProductRanking()
}
```

目标逻辑：

```ts
if (canResolve('product_id') && hasCountableRecords()) {
  enableProductRanking()
}
```

优化清单：

- [ ] 类目排行依赖可解析的 `category_id` 或类目名称，不依赖 `products` 角色。
- [ ] 商品排行依赖可解析的 `product_id` 或商品名称，不依赖固定商品表。
- [ ] 渠道分析依赖地区、设备或渠道维度，不依赖固定用户表。
- [ ] 销售额指标根据金额业务含义和粒度决定，不仅检查 `amount` 字段名。
- [ ] RFM 根据用户、交易时间和交易价值决定能力，不依赖订单角色。
- [ ] 指标结果保留原始键和展示标签，避免名称冲突后无法追溯。
- [ ] 指标不可用时准确列出缺失字段、未确认关系或口径问题。

验收标准：

- [ ] 只有行为表和 `category_id` 时，可以按 ID 展示类目排行。
- [ ] 再上传类目对照表并确认关系后，排行自动切换为类目名称。
- [ ] 对照表部分 ID 缺失时，其余数据仍正常展示。
- [ ] 删除或停用关系后，结果安全回退为原始 ID。

## 10. 看板与业务建议

- [ ] 看板图表优先展示关系解析后的名称。
- [ ] Tooltip 同时保留原始 ID，便于核对。
- [ ] 对未匹配数据使用“未知”或原始 ID，并显示数量。
- [ ] 业务建议基于最新指标结果生成，不读取旧缓存。
- [ ] 建议中标明所用数据范围、筛选条件和关键口径。
- [ ] 关系或数据存在风险时，在数据诊断中提示，不混入正常业务结论。

## 11. AI 助手改造

- [ ] AI 上下文包含表结构、已确认关系和数据版本。
- [ ] 本地分析工具支持按关系解析名称。
- [ ] AI 的结构化结果同时包含原始 ID 与展示名称。
- [ ] AI 只能使用已确认关系，不能自行采用低置信度候选关系。
- [ ] AI 回答注明实际筛选条件、数据范围和计算口径。
- [ ] 当关系未确认时，AI 明确说明只能按原始 ID 分析。
- [ ] 数据或关系变化后，旧对话中的缓存分析结果应失效或标记为历史结果。

## 12. 性能与缓存

- [ ] 使用 `Map` 和 `Set` 建立连接键索引，禁止全量嵌套循环匹配。
- [ ] 候选发现使用抽样，候选确认使用全量或分批验证。
- [ ] 缓存关系索引和名称映射字典。
- [ ] 以数据版本、映射版本和关系版本作为缓存键。
- [ ] 映射或关系变化时只失效受影响的指标。
- [ ] 大计算迁移到 Web Worker，避免阻塞页面交互。
- [ ] 设定浏览器端推荐文件大小和行数上限。
- [ ] 对超限数据给出明确提示，后续预留服务端计算方案。

## 13. 数据正确性与风险控制

- [ ] 所有自动关系必须可查看依据、可撤销、可回退。
- [ ] 中低置信度关系不能静默进入指标计算。
- [ ] 多对多关系第一阶段禁止自动启用。
- [ ] 金额指标必须声明粒度和去重策略。
- [ ] 连接维度表不得改变事实指标的基础记录数。
- [ ] 关系启用前后对关键指标执行一致性检查。
- [ ] 重复主键、冲突名称和低匹配率进入数据诊断。
- [ ] 对错误配置提供恢复默认建议，但不覆盖用户数据。

关键保护规则：

```text
自动发现 ≠ 自动信任
名称映射 ≠ 事实表直接展开
字段同名 ≠ 一定能够关联
存在 amount ≠ 一定可以计算销售额
关系确认后才允许进入正式分析
```

## 14. 测试清单

### 14.1 字段识别

- [ ] 同名同语义字段能够识别。
- [ ] 异名同语义字段经过映射后能够识别。
- [ ] 同名不同语义字段不会仅凭名称自动确认。
- [ ] 用户手动映射优先级高于自动推断。

### 14.2 关系发现

- [ ] `category_id → category_name` 自动发现成功。
- [ ] 右侧主键唯一时识别为多对一关系。
- [ ] 右侧主键重复且名称冲突时禁止启用。
- [ ] 匹配率过低时只提示，不自动确认。
- [ ] 多个候选维度表时要求用户选择。
- [ ] 数字 ID 与字符串 ID 在安全标准化后可以匹配。
- [ ] 前导零有业务意义时不会被错误删除。

### 14.3 指标与展示

- [ ] 没有对照表时按原始 ID 展示排行。
- [ ] 确认关系后切换为名称展示。
- [ ] 未匹配值正确回退。
- [ ] 关系变化后指标和 AI 上下文同步刷新。
- [ ] 名称映射不改变销售额、订单数和行为数。
- [ ] 现有固定角色数据集保持兼容。

### 14.4 性能

- [ ] 多文件导入时页面不出现长时间无响应。
- [ ] 关系发现没有字段间全量笛卡尔比较。
- [ ] 重复查看看板能够复用有效缓存。
- [ ] 大文件达到限制时给出可理解的诊断。

## 18. 最终验收标准

- [ ] 上传一种新对照表时，不需要新增 `FileRole` 才能使用。
- [ ] 指标能力主要由字段和已确认关系决定。
- [ ] 用户可以看懂、确认和撤销自动关系。
- [ ] 错误或低质量关系不会静默影响业务指标。
- [ ] 名称映射不会造成金额和记录数重复计算。
- [ ] 字段配置、能力清单、看板、业务建议和 AI 实时同步。
- [ ] 现有固定角色数据和已实现功能保持兼容。
- [ ] 系统明确说明无法分析的原因和修复方式。
