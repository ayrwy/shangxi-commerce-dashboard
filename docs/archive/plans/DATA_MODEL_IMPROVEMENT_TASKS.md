# CSV 导入与数据建模改进清单

## 1. 当前判断

- 多表方案的主干方向正确：先识别表角色，再映射字段，最后按 `order_id`、`product_id`、`user_id` 检查关系，并在各自粒度计算指标。
- 多表方案仍不是“完全没有问题”：当前实现对重复角色、手动关系配置、关系基数、宽表和复杂退款场景支持有限。
- 单表模式是下一阶段最值得优先补强的部分，尤其是订单宽表、订单明细单表以及自定义业务表。
- 在真实看板接入之前，必须先稳定“数据粒度、字段语义、关系和指标口径”，否则看板会放大错误结果。

## 2. 推荐推进顺序

1. P0：补齐建模安全性，防止用户成功确认错误模型。
2. P1：增强单表模式，使常见的一张 CSV 能得到明确、正确的指标结果。
3. P2：增强多表关系配置和多文件合并能力。
4. P3：引入真实指标引擎并驱动经营看板。
5. P4：解决超大文件、平台模板和高级建模。

## P0：建模安全性补强

### 任务 20：增加“每行代表什么”确认

- [ ] 在文件角色之前显示粒度选择：一次行为、一个订单、一个订单商品、一个商品、一个用户、一次退款、自定义。
- [ ] 自动推荐粒度，但必须允许用户修改。
- [ ] 用示例说明粒度，例如“同一个 `order_id` 可以出现多行，说明可能是订单商品粒度”。
- [ ] 粒度与文件角色冲突时显示阻断错误。

验收：用户在映射字段前能够回答“这张表的一行代表什么”。

### 任务 21：阻止同一文件重复映射标准字段

- [ ] 同一文件内默认禁止两列同时映射成同一个标准字段。
- [ ] 如果确实需要多列合并，进入单独的字段转换流程。
- [ ] 显示重复映射的列名和修复入口。

验收：`goods_id` 和 `sku_id` 不能在没有说明的情况下同时成为 `product_id`。

### 任务 22：校验角色必需字段

- [ ] 用户行为表至少需要 `behavior`，计算购买用户数还需 `user_id`。
- [ ] 订单主表至少需要 `order_id` 和 `order_amount`，或选择其他明确的 GMV 口径。
- [ ] 订单明细至少需要 `order_id`、`product_id`，计算销售额还需 `price` 和 `amount`。
- [ ] 商品表至少需要唯一的 `product_id`。
- [ ] 用户表至少需要唯一的 `user_id`。
- [ ] 退款表计算退款率时必须明确退款分子和分母。

验收：角色缺少关键字段时不能显示对应指标“可用”。

### 任务 23：处理重复角色文件

- [ ] 检测上传两个订单主表、两个商品表等情况。
- [ ] 让用户选择：纵向合并、分别作为不同数据集、替换已有文件或取消。
- [ ] 未选择处理方式前阻止确认。
- [ ] 不再由程序静默使用同一角色的第一张表。

验收：上传两张订单主表时，结果不依赖文件上传顺序。

### 任务 24：统一指标口径说明

- [ ] 每个指标显示来源表、粒度、公式和去重键。
- [ ] GMV 示例：`订单主表.order_amount` 按 `order_id` 去重求和。
- [ ] 行为 GMV 示例：仅 `behavior=buy`，计算 `price * amount`。
- [ ] 退款率明确采用金额退款率还是订单退款率。

验收：用户可以查看“这个数字是怎样算出来的”。

## P1：单表模式增强

### 任务 25：建立单表类型识别器

- [ ] 识别用户行为单表。
- [ ] 识别订单主表单表。
- [ ] 识别订单明细单表。
- [ ] 识别订单宽表，即一张表同时包含订单字段和商品字段。
- [ ] 无法判断时要求用户选择，不进行强制猜测。

验收：四种标准单表分别得到正确推荐和说明。

### 任务 26：完善用户行为单表

- [ ] 支持 `pv/fav/cart/buy` 及常见中文别名。
- [ ] 显示行为值分布，允许用户确认哪些值代表浏览、收藏、加购、购买。
- [ ] 无 `order_id` 时只显示购买行为数，不显示真实订单量。
- [ ] `price` 或 `amount` 缺失时，GMV 不可用但漏斗仍可用。
- [ ] 支持把 `address`、`sex`、`device` 映射成分析维度，而不是只能忽略。

验收：`UserBehavior1.csv` 可以正确得到漏斗、购买用户、购买行为和 GMV 能力说明。

### 任务 27：支持订单主表单表

- [ ] 按 `order_id` 计算订单量。
- [ ] 按订单粒度计算 GMV、客单价和购买用户数。
- [ ] 有 `channel` 时计算渠道贡献。
- [ ] 有时间字段时计算趋势和复购相关能力。
- [ ] 明确说明没有商品明细时商品排行不可用。

验收：只上传订单主表也能得到一组正确但有限的经营指标。

### 任务 28：支持订单明细单表

- [ ] 使用 `price * amount` 计算明细销售额。
- [ ] 有 `order_id` 时计算去重订单量。
- [ ] 计算商品销量、商品销售额和商品排行。
- [ ] 没有 `user_id` 时不显示购买用户和复购率。
- [ ] 明确区分“明细销售额”和“订单实付 GMV”。

验收：只有订单明细表时不再被错误地要求必须补充订单主表。

### 任务 29：支持订单宽表

- [ ] 自动检测 `order_id` 重复且 `order_amount` 重复出现的宽表。
- [ ] 订单量按 `order_id` 去重。
- [ ] 订单 GMV按每个 `order_id` 取一次 `order_amount`。
- [ ] 商品指标按每一条明细行计算。
- [ ] 检测同一订单出现多个不同 `order_amount`，作为阻断错误。

验收：一个订单包含多个商品时，GMV 不会因为行数增加而重复累计。

### 任务 30：增加自定义字段维度

- [ ] 允许将无法识别的字段标记为文本维度、数值维度、日期维度或忽略。
- [ ] 支持 `sex`、`address`、`device` 等非核心字段进入后续分析。
- [ ] 检测字段类型并允许人工修改。

验收：未知字段不再只能选择“不映射”。

## P2：多表模式增强

### 任务 31：增加可视化关系确认页

- [ ] 用节点展示所有上传表。
- [ ] 用连线展示 `orders -> order_items`、`products -> order_items` 等关系。
- [ ] 显示关系字段、匹配率和未匹配数量。
- [ ] 允许用户修改关系字段。

验收：用户能够看懂哪张表通过什么字段连接到哪张表。

### 任务 32：增加关系基数校验

- [ ] 支持一对一和一对多。
- [ ] 默认不允许未经确认的多对多关系。
- [ ] 检查“一端”字段是否唯一。
- [ ] 检查空键、重复键和数据类型不一致。

验收：商品表的 `product_id` 重复时，不能继续声明商品表到明细表是一对多。

### 任务 33：完善外键质量报告

- [ ] 显示匹配率、匹配行数、未匹配行数和示例键值。
- [ ] 区分缺失维度和孤立事实记录。
- [ ] 允许设置警告阈值和阻断阈值。
- [ ] 说明未匹配关系会影响哪些指标。

验收：用户可以定位具体哪些订单、商品或用户没有匹配。

### 任务 34：支持同角色文件纵向合并

- [ ] 校验多文件表头是否兼容。
- [ ] 支持按月份、平台或店铺合并订单文件。
- [ ] 自动补充来源文件、平台、店铺等追踪字段。
- [ ] 对字段缺失或类型冲突提供合并预览。

验收：多个同结构月度订单 CSV 可以作为一张逻辑订单表使用。

### 任务 35：完善退款模型

- [ ] 支持订单退款率：退款订单数 / 支付订单数。
- [ ] 支持金额退款率：退款金额 / GMV。
- [ ] 支持一笔订单多次退款并按退款记录粒度汇总。
- [ ] 防止退款表连接订单明细后重复累计退款金额。

验收：页面不再笼统显示一个没有口径说明的“退款率”。

## P3：真实指标与经营看板

### 任务 36：建立统一分析数据模型

- [ ] 把确认后的文件、字段、粒度和关系转换成统一模型配置。
- [ ] 模型配置可序列化、恢复和版本化。
- [ ] 看板不直接读取原始字段名，只读取标准字段和指标。

### 任务 37：引入真实指标计算引擎

- [ ] 使用 DuckDB-Wasm、SQL 或等价列式计算方案。
- [ ] 指标按各自粒度聚合后再组合。
- [ ] 支持筛选条件下重新计算。
- [ ] 为每个指标增加口径测试。

### 任务 38：让看板切换数据来源

- [ ] 增加“示例数据 / 上传数据”来源状态。
- [ ] 上传数据可用时允许切换或自动进入真实数据模式。
- [ ] 指标不可用时显示原因，不回退为假数字。
- [ ] 所有图表显示当前数据来源和更新时间。

### 任务 39：建立真实看板最小闭环

- [ ] 用户行为表驱动 GMV、购买用户、购买行为和漏斗。
- [ ] 订单模型驱动 GMV、订单量、客单价和趋势。
- [ ] 订单明细驱动商品排行。
- [ ] 渠道字段驱动渠道贡献。
- [ ] 退款模型驱动退款金额和退款率。

验收：上传模板数据后，看板数字与离线基准结果一致。

## P4：性能与高级能力

### 任务 40：大文件分块解析

- [ ] 使用 Web Worker 避免阻塞界面。
- [ ] 流式或分块解析，不把全部 CSV 文本和数组同时保存在主线程。
- [ ] 显示解析进度、预计剩余时间和取消入口。
- [ ] 对 50 MB、100 MB 和 500 MB 文件分别做性能基准。

### 任务 41：替换 sessionStorage 数据保存

- [ ] 原始文件和完整行数据使用 IndexedDB 或本地数据库。
- [ ] `sessionStorage` 只保存轻量模型配置和页面状态。
- [ ] 会话恢复时校验原始文件是否仍可用。

### 任务 42：字段转换和清洗

- [ ] 日期格式转换。
- [ ] 金额单位和货币处理。
- [ ] 文本去空格、大小写和枚举归一化。
- [ ] 多列合并、拆分和默认值。

### 任务 43：平台模板适配

- [ ] 抖音、天猫、京东、小红书等常见导出格式模板。
- [ ] 模板版本识别和变更提示。
- [ ] 平台字段先转换到统一标准模型，再进入指标计算。

## 3. 每项任务的统一完成标准

每个任务只有同时满足以下条件才算完成：

- [ ] 有明确的用户场景和输入样例。
- [ ] 有正常、缺字段、异常值和边界数据测试。
- [ ] 页面能解释自动推荐的原因。
- [ ] 用户可以人工纠正自动推荐。
- [ ] 错误不会生成看似正常的指标。
- [ ] `npm test` 和 `npm run build` 通过。
- [ ] 更新对应规格与验收记录。

## 4. 建议下一步

优先从任务 20、22、23 开始。这三项先把数据粒度、必需字段和重复角色规则固定下来；完成后再做任务 25-29 的单表增强，可以避免同一套判断逻辑反复返工。
