# 数据导入与自适应看板改进清单

## 1. 改造目标

将当前依赖固定文件类型和固定看板结构的 Demo，改造成“字段能力驱动”的自适应分析平台。

目标流程：

```text
上传 1-8 个 CSV
→ 自动识别平台支持的字段
→ 用户只确认存在歧义的映射
→ 按需验证跨文件关系
→ 生成当前数据的分析能力清单
→ 看板只展示能够可靠计算的真实图表
```

核心原则：

- 接受字段名称、顺序和文件数量不固定的 CSV。
- 不承诺任意 CSV 都能生成完整看板。
- 数据具备什么能力，就展示什么分析。
- 可选维度缺失不影响核心指标。
- 真实数据、示例数据严格分离，不允许静默混用。
- 无法计算时说明原因，不显示无解释的空白图表。

## 2. 精简数据导入入口

### 2.1 单一上传入口

- 数据导入页只保留一个上传区域。
- 支持点击选择和拖放上传。
- 单次允许上传 1-8 个 CSV。
- 显示文件名、大小、行数、列数、解析状态和错误信息。
- 允许追加、替换、移除和重新解析文件。

### 2.2 自动完成基础识别

系统在上传后自动处理：

- 文件编码和分隔符识别。
- 表头、数据类型和日期格式识别。
- 字段别名映射。
- 金额、数量、编号、时间和文本字段推断。
- 行粒度和主键候选推断。
- 同类文件候选识别。
- 跨文件连接键候选识别。
- 当前数据可支持的分析能力检测。

### 2.3 只展示需要确认的内容

字段确认页默认只显示：

- 已映射到平台标准字段的列。
- 低置信度或存在歧义的列。
- 可能影响指标口径的关键字段。

未识别或与平台分析无关的字段放入“其他字段”，默认设为忽略并折叠展示。

用户可手动修改映射，但只能选择平台支持的标准字段或“忽略”。

## 3. 统一标准字段

第一版建议支持以下标准字段：

| 类别 | 标准字段 | 含义 |
|---|---|---|
| 时间 | `datetime` | 交易、行为或记录发生时间 |
| 金额 | `sales_amount` | 实付金额或可用于 GMV 的销售金额 |
| 金额 | `order_amount` | 订单口径金额 |
| 金额 | `refund_amount` | 退款金额 |
| 商品 | `price` | 商品单价 |
| 商品 | `quantity` | 商品数量 |
| 订单 | `order_id` | 订单唯一标识 |
| 用户 | `user_id` | 用户唯一标识 |
| 商品 | `product_id` | 商品或 SKU 唯一标识 |
| 商品 | `product_name` | 商品名称 |
| 商品 | `category` | 商品品类 |
| 属性 | `channel` | 渠道或来源 |
| 属性 | `device` | 用户设备 |
| 属性 | `address` | 原始地址 |
| 属性 | `province` | 省份 |
| 属性 | `city` | 城市 |
| 属性 | `occupation` | 职业或职位 |
| 属性 | `user_segment` | 用户分群、等级或标签 |
| 行为 | `behavior` | 浏览、收藏、加购、购买等行为 |
| 退款 | `refund_order_id` | 退款关联订单标识 |
| 退款 | `refund_at` | 退款时间 |

必须避免继续使用含义模糊的 `amount` 同时代表金额和数量。金额、单价、数量和退款金额必须分别映射。

## 4. 从文件类型驱动改为分析能力驱动

系统不再要求每个文件必须完全符合某个固定模板，而是根据已确认字段、行粒度和关系判断可以计算什么。

### 4.1 基础层

最低条件：

```text
datetime + sales_amount
```

可生成：

- 销售额。
- 销售趋势。
- 按日、周、月聚合。
- 数据日期范围。

如果只有金额没有日期，可以显示总销售额，但不能生成时间趋势。

### 4.2 订单层

最低条件：

```text
order_id
```

可生成：

- 去重订单数。
- 同时具备销售金额时计算客单价。
- 订单趋势需要同时具备日期。

必须根据行粒度判断是否需要按 `order_id` 去重，避免订单明细重复计算。

### 4.3 用户层

最低条件：

```text
user_id + 可确认的购买依据
```

购买依据可以是订单记录，或归一化后的 `behavior=purchase`。

可生成：

- 购买用户数。
- 用户购买频次。
- 复购率。
- 用户趋势。

只有 `user_id` 时只能计算用户出现数，不能直接称为购买用户或复购率。

### 4.4 商品层

最低条件之一：

```text
product_id + sales_amount
```

或：

```text
product_id + price + quantity
```

可生成：

- 商品销售额排行。
- 商品销量排行。
- 商品趋势。

如果存在 `category`，可进一步生成品类销售额和销量排行；品类缺失不影响商品分析。

### 4.5 可选属性和来源层

以下字段全部属于可选分析维度：

```text
channel
device
address / province / city
occupation
user_segment
category
```

这些字段不是核心分析的必需条件。系统应先根据事实字段生成核心指标，再根据实际存在的可选维度为已有指标增加分组、筛选或画像视图。

例如：

- 存在 `channel` 时，增加按渠道查看和筛选。
- 存在 `device` 时，增加设备分布或按设备拆分。
- 存在省市字段时，增加地区分布。
- 存在职业或用户分群时，增加用户画像。
- 不存在这些字段时，直接隐藏相应模块，不影响其他分析。

不需要预先穷举所有“维度 × 指标”组合，也不能把 `channel` 等字段当成每份数据的必需字段。

### 4.6 退款层

可根据已有字段逐步开放：

- 有 `refund_amount`：退款金额。
- 有退款订单标识：退款订单数。
- 同时有销售金额：金额退款率。
- 同时有全部订单数：订单退款率。
- 有退款时间：退款趋势。

只有退款分子、没有销售或订单分母时，应显示退款金额或退款订单数，但不能生成退款率。

### 4.7 行为层

最低条件：

```text
behavior
```

可生成：

- 行为次数分布。
- 行为次数漏斗。
- 同时有 `user_id` 时生成去重用户漏斗。
- 同时有日期时生成行为趋势和路径分析。

行为值需要先归一化：

```text
pv / view / 浏览       → view
fav / collect / 收藏   → favorite
cart / add_cart / 加购 → cart
buy / pay / 购买       → purchase
```

## 5. 可选维度的正确定位

字段分为三类：

| 类型 | 示例 | 作用 |
|---|---|---|
| 时间字段 | `datetime` | 时间筛选和趋势 |
| 事实与标识字段 | `sales_amount`、`order_id`、`user_id`、`behavior` | 决定核心指标能力 |
| 可选维度 | `channel`、`device`、`category`、`province` | 增强已有指标的分组和筛选 |

能力检测顺序：

```text
先检测核心指标
→ 再检测可选维度
→ 为可用指标增加分组方式
```

可选维度不存在时，不应显示错误，也不应阻止进入看板。只有在“解锁更多分析”区域中才提示用户可补充哪些字段。

## 6. 多文件关系处理

### 6.1 单表分析优先

一个分析所需字段都在同一文件中时，直接计算，不要求用户建立关系。

### 6.2 跨表时才验证关系

当指标所需字段分散在多个文件时，系统使用相同标准字段生成候选关系，例如：

```text
订单表.order_id → 订单明细.order_id
订单明细.product_id → 商品表.product_id
退款表.order_id → 订单表.order_id
```

相同字段只能说明“可能关联”，不能无条件直接连接。系统需要自动检查：

- 空值率。
- 唯一率。
- 两侧匹配率。
- 编号格式是否一致。
- 一对一、一对多或多对多基数。
- 是否需要平台、店铺等复合键。
- 关联后是否会造成金额和订单重复计算。

安全关系可自动使用；低匹配率、多对多或可能重复计算的关系才要求用户确认。

### 6.3 同类文件处理

- 表头兼容且角色一致的文件可以纵向合并。
- 保留 `_source_file` 字段用于追踪来源。
- 表头不一致时展示差异，并让用户确认缺失列处理方式。
- 不允许默认按上传顺序选择其中一张文件。

## 7. 分析能力清单

字段确认后，系统生成清晰的能力清单：

```text
可直接计算
✓ 销售额与销售趋势
✓ 订单量与客单价
✓ 购买用户与复购率
✓ 行为漏斗

需要确认
△ amount 可能是金额或数量
△ 浏览、购买行为值需要归一化

需要关系
△ 品类销售额需要关联商品表

当前不可用
— 退款率：没有退款数据
```

建议能力状态统一为：

```text
available             可直接计算
needs_confirmation    需要确认口径
missing_relation      缺少或需要确认关系
missing_fields        缺少必要字段
```

每项能力记录：

- 指标名称。
- 当前状态。
- 使用的字段和文件。
- 计算口径。
- 去重键。
- 缺少字段或关系。
- 风险和建议操作。

## 8. 动态看板

### 8.1 根据能力动态生成模块

- 只渲染当前真实数据能够可靠计算的指标和图表。
- 可选维度存在时增加筛选器或分组视图。
- 不可用模块默认不占据大面积看板空间。
- 可以在页面底部提供“补充数据可解锁”区域。

### 8.2 禁止真实数据与示例数据混用

- 用户选择真实数据后，所有指标、图表、目标和简报必须来自真实数据。
- 空结果不能回退到示例数据。
- 示例数据只有用户明确选择时才显示。
- 页眉、侧边栏、指标卡和图表的数据来源状态必须一致。

### 8.3 明确处理不可用和空结果

每个模块至少支持以下状态：

- 正常结果。
- 当前筛选范围没有数据。
- 缺少必要字段。
- 关系尚未确认。
- 字段口径尚未确认。
- 计算错误。

示例：

```text
渠道分析未生成
当前数据没有渠道字段，不影响销售、订单和用户分析。
```

```text
商品排行暂不可用
需要 product_id + sales_amount，或 product_id + price + quantity。
```

禁止显示没有说明的空白坐标轴。

### 8.4 时间范围改进

- 真实数据默认选择“全部数据”。
- 自动显示上传数据的最早和最晚日期。
- 支持近 7 天、近 14 天、近 28 天、全部数据和自定义范围。
- 近 N 天应优先以数据最大日期作为锚点，而不是只以系统当前日期为锚点。
- 当前范围为空时给出明确提示。

## 9. 数据标准化

### 9.1 地址标准化

- 保留原始 `address`。
- 尽可能派生 `province`、`city`、`district`。
- 未标准化前只能显示原始地址分布，不能宣称是可靠地区贡献。

### 9.2 用户属性标准化

- 不使用含义固定且不通用的 `user_face`。
- 优先使用 `occupation`、`job_title`、`user_segment` 等通用语义。
- 允许将会员等级、新老用户、客户类型等映射为用户分群。

### 9.3 金额和数量校验

- 检查金额字段是否包含货币符号和千位分隔符。
- 检查数量字段是否主要为小整数。
- 检查 `price × quantity` 是否与销售金额接近。
- 发现异常时要求用户确认，不自动套用错误口径。

## 10. 页面文案与状态同步

- 删除“仅完成结构确认，当前看板仍使用示例数据”等过期文案。
- 确认成功后显示“上传数据已接入真实指标计算”。
- 同时说明可用图表取决于已映射字段和已确认关系。
- 页面中的经营建议必须基于真实指标生成；条件不足时隐藏或显示暂不可用。
- 不再显示固定的模拟商品、渠道和退款建议。

## 11. 技术模块改造

### 11.1 字段识别器

识别依据不只包含字段名，还应综合：

- 文件名。
- 样例值。
- 数据类型。
- 唯一率。
- 空值率。
- 数值范围。
- 与其他字段的组合关系。

### 11.2 能力检测器

建立统一能力描述：

```ts
type AnalysisCapability = {
  key: string
  label: string
  status: 'available' | 'needs_confirmation' | 'missing_relation' | 'missing_fields'
  sourceFiles: string[]
  fields: string[]
  dimensions: string[]
  definition: string
  dedupKey?: string
  missingFields?: string[]
  reason?: string
}
```

### 11.3 统一分析模型

将原始文件映射成逻辑分析表，而不是让看板直接读取 CSV：

```text
fact_sales
fact_orders
fact_order_items
fact_behaviors
fact_refunds
dim_users
dim_products
```

第一阶段不必生成实体数据库表，但内部模型应明确：

- 行粒度。
- 主键和去重键。
- 标准字段。
- 文件来源。
- 可用关系。
- 指标计算口径。

### 11.4 指标引擎

- 指标根据能力状态注册和执行。
- 每个指标明确所需字段、关系、粒度和去重键。
- 分组维度作为可选参数，而不是固定写死渠道、商品等分支。
- 所有看板模块共享统一筛选条件。

## 12. 实施优先级

### P0：修复当前产品边界

- 删除过期的示例数据文案。
- 真实数据与示例数据完全隔离。
- 空白图表改成原因提示。
- 修复分析模式根据已确认字段和角色自动推导。
- “全部数据”作为真实数据默认范围。
- 修复订单去重、金额和数量口径。

### P1：完成自适应导入第一版

- 单一多文件上传入口。
- 自动字段映射和用户确认。
- 只展示平台支持字段。
- 自动忽略无关字段。
- 建立新的能力检测器。
- 看板按能力动态显示模块。
- 增加商品和品类排行。
- 支持可选渠道、设备、地区和用户属性维度。

### P2：增强多文件和数据标准化

- 候选关系生成和基数验证。
- 同类文件纵向合并。
- 行为值归一化。
- 地址省市解析。
- 金额和数量语义校验。
- 保存用户确认的字段映射模板。

### P3：生产化能力

- 大文件分块和后台计算。
- 数据集持久化。
- Excel 和平台报表模板适配。
- 字段转换与计算字段。
- 数据质量报告。
- 真实经营建议引擎。

## 13. 验收标准

完成第一阶段改造后，应满足：

- 用户可以通过一个入口上传不超过 8 个 CSV。
- 系统只要求用户确认有歧义的关键字段。
- 无渠道、设备、地址等可选字段时仍能完成核心分析。
- 单表具备必要字段时可以直接生成对应图表。
- 跨表分析只在关系验证安全后启用。
- 看板不再显示无说明的空白模块。
- 真实数据模式不会混入模拟指标或固定建议。
- 每个指标都能说明来源字段、计算公式和去重口径。
- 缺少字段时明确说明限制，但不阻断其他可用分析。

## 14. 最终产品定义

产品不应承诺“任何 CSV 都能生成完整看板”，而应承诺：

> 接受结构和字段不固定的 CSV，自动识别平台支持的字段，让用户只确认必要歧义，并根据能够可靠计算的事实字段、可选维度和安全关系生成对应的真实分析。

这次改造的本质，是把系统从“猜中固定模板才能使用”升级为“数据具备什么分析能力，就可靠地展示什么”。
