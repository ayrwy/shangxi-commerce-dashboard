# 商析（暂定名）项目计划

> 版本：v0.1 Demo 规划  
> 更新时间：2026-07-25  
> 状态：已确认方向，准备进入首版实现

## 1. 产品定位

商析是一套面向电商负责人、运营经理和店铺老板的经营分析驾驶舱。

首要任务不是展示尽可能多的图表，而是在 30 秒内回答：

1. 生意现在怎么样？
2. 变化由什么造成？
3. 下一步应该优先做什么？

产品体验围绕以下决策链设计：

```text
经营结果 -> 发现异常 -> 定位渠道/商品/用户 -> 解释原因 -> 采取行动
```

## 2. 首版 Demo 目标

首版先完成一条完整、可演示的体验链路：

```text
示例数据 / 多个 CSV 上传入口
        -> 数据概览
        -> 经营总览看板
        -> 商品 / 用户 / 渠道分析入口
```

首版必须具备：

- 一套完整的模拟电商数据
- 可交互的经营总览
- 统一的图表渲染组件
- 日期、渠道等基础筛选
- 多文件上传入口和上传状态反馈
- 空状态、加载状态、异常提示
- 可在桌面端运行，并在窄屏下保持可浏览

## 3. 首版页面范围

### 3.1 经营总览

- GMV / 销售额
- 订单量
- 客单价
- 转化率
- 退款率
- 目标完成进度
- 销售趋势与经营事件时间线
- 渠道贡献
- 商品机会矩阵或商品排行
- 今日经营洞察与行动建议

### 3.2 商品分析

- 商品销售排行
- 销售额、销量、转化率对比
- 爆款、潜力款、问题款标签
- 商品详情抽屉

### 3.3 用户分析

- 新客与老客结构
- 购买用户数
- 复购率趋势
- 用户价值分层的演示视图

### 3.4 渠道分析

- 渠道销售额和订单量对比
- 渠道贡献占比
- 访问到支付的漏斗演示
- 渠道趋势和经营建议

### 3.5 数据导入

- 批量选择多个 CSV
- 展示文件名、大小、状态
- 展示基础行数 / 列数预览（可先用前端解析）
- 提供“继续配置字段”的下一步入口
- 提供下载示例模板的入口

## 3.6 单表用户行为数据模式

当用户只有类似 UserBehavior1.csv 的单表时，文件角色配置为“用户行为明细表”，不强行映射为订单主表。支持字段：

- 用户维度：user_id、sex、address、device
- 商品维度：goods_id、category_id
- 行为维度：behavior（pv / fav / cart / buy）
- 时间维度：datetime
- 交易字段：price、amount

行为模式中的指标口径：

- GMV = sum(price × amount)，仅统计 behavior = buy
- 购买件数 = sum(amount)，仅统计 behavior = buy
- 购买用户数 = 去重 user_id，仅统计 behavior = buy
- 订单量暂以购买行为行数近似，并明确标注“购买行为数”
- 漏斗按 pv → fav → cart → buy 展示
- 没有 order_id 时不声称是真实订单量
- 没有退款字段时退款率显示为“暂无数据”
- 没有渠道字段时渠道贡献显示为“暂无数据”

## 4. 数据策略

### 4.1 Demo 阶段

- 使用本地模拟数据驱动全部看板
- 模拟数据需要覆盖订单、订单明细、商品、用户、渠道、退款和经营事件
- 交互筛选必须真正改变指标和图表，而不是只改变选中状态
- CSV 上传先实现文件接收、文件列表和基础预览

### 4.2 后续真实数据阶段

后续再接入以下数据链路：

```text
多 CSV 上传
  -> 文件角色识别
  -> 标准字段映射
  -> 数据质量检查
  -> 表关系确认
  -> DuckDB / SQL 指标计算
  -> 看板生成
```

初期支持的常见实体：

- 订单主表
- 订单商品明细
- 商品表
- 用户表
- 退款表

指标必须保留数据粒度，避免多表关联后重复计算。订单指标在订单粒度计算，商品销量在明细粒度计算，退款金额在退款粒度计算。

## 5. 技术方案

- 前端：React + TypeScript + Vite
- 图表：ECharts，通过统一 `ChartRenderer` 渲染
- 样式：自建 CSS 设计系统，不直接套用后台模板
- 状态：首版使用 React 本地状态和配置对象
- 数据：首版本地 TypeScript 模拟数据；后续接入 DuckDB / API
- 配置：指标、图表和看板布局采用 JSON / TypeScript 配置驱动

统一图表协议至少支持：

- `metric`：指标卡
- `line`：趋势折线图
- `bar`：排行条形图
- `pie`：渠道 / 类目占比
- `scatter`：商品机会矩阵
- `funnel`：转化漏斗
- `table`：数据表格

业务模块不直接依赖 ECharts option。业务数据先转换成平台自己的图表配置，再由渲染器映射成 ECharts 配置。

## 6. AI 边界

AI 不是首版的数值计算器。

### 程序 / 规则引擎负责

- 读取和清洗数据
- 字段类型判断
- 去重、缺失值和异常值检查
- 指标计算
- 查询安全校验
- 图表数据准备

### AI 负责

- 辅助判断字段语义
- 解释已经计算出的趋势和异常
- 生成经营摘要和行动建议
- 后续支持自然语言提问

AI 不得直接编造数字，也不得绕过受控指标查询直接回答经营数据问题。

## 7. 视觉系统

### 7.1 方向

视觉关键词：经营简报、交易脉搏、清晰、克制、有现场感。

避免做成传统蓝色后台、深色科技大屏或无差别卡片墙。

### 7.2 色彩 Token

- 瓷白底：`#F5F7F8`
- 墨蓝字：`#172126`
- 钴蓝主色：`#2864DC`
- 交易橙：`#FF7A45`
- 增长青：`#13A88A`
- 雾灰边界：`#E8EDF0`

### 7.3 字体与排版

- 标题：优先使用系统中文无衬线字重变化，突出短句和结论
- 正文：清晰、紧凑，避免营销化长文案
- 数据：使用等宽或数字感较强的字体处理关键数值
- 大量留白配合细分隔线，避免每个区域都变成厚重卡片

### 7.4 视觉记忆点

“经营脉搏”是一条贯穿首屏的销售趋势线，直播、补货、价格调整和退款高峰等经营事件直接标注在线上，让波动和发生的事情对应起来。

## 8. 交互原则

- 筛选后指标、图表和洞察同步更新
- 点击异常指标可以打开原因分析抽屉
- 点击商品或渠道可以联动其他区域
- 上传文件后立刻反馈状态，不让用户等待时无反馈
- 无法计算的模块要说明缺少什么字段，而不是显示空白
- 所有重要按钮使用明确动词，例如“上传文件”“查看商品”“确认字段”
- 尊重减少动态效果设置，并保留键盘焦点样式

## 9. 明确不做的事情

首版不包含：

- 淘宝、京东、抖音等平台官方 API 接入
- 复杂的账号权限和团队协作
- 账单、订阅和生产部署
- 任意复杂数据库关系的全自动推断
- 让 AI 直接计算或生成未经查询验证的数字
- 完全自由的 AI 自动排版
- 覆盖所有行业和所有 CSV 格式

## 10. 实施顺序

1. 建立前端项目和基础设计 Token
2. 建立模拟数据与指标配置
3. 实现 `ChartRenderer` 和基础图表组件
4. 完成经营总览页面
5. 加入日期、渠道筛选和详情抽屉
6. 完成商品、用户、渠道页面
7. 加入多文件上传面板和基础 CSV 预览
8. 做构建检查、响应式检查和视觉自检
9. 再进入字段映射、关系确认、DuckDB 指标计算

## 11. 验收标准

首版 Demo 在交付时应满足：

- 可以启动并打开一个完整的中文经营分析页面
- 页面不是静态图片，筛选和主要点击可交互
- 图表由统一渲染组件驱动
- 示例数据足够支撑首页叙事，不出现大片空白
- CSV 上传入口可以选择多个文件并展示文件状态
- 页面在常见桌面宽度下布局稳定
- 构建命令通过，无明显 TypeScript 错误
- 后续接入真实数据时，不需要推翻页面结构

## 12. 偏离处理规则

后续如果出现新需求，先判断它属于：

1. 首版必须能力：可以直接加入当前迭代
2. 首版增强能力：记录为后续迭代，不打断主链路
3. 会改变产品边界的能力：先更新本文件，再开始实现

任何涉及真实数据计算、AI 自动决策、外部平台接入或权限体系的变化，都必须先更新本计划中的范围、数据策略和验收标准。
